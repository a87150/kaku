## 3. P0 详情

### C-01 文章编辑：鉴权写在写入之后

**位置**：`written/views.py:201-205`

```python
def post(self, request, *args, **kwargs):
    response = super().post(request, *args, **kwargs)   # ← 这里已经 save() 落库了
    if self.request.user != self.object.author:
        return HttpResponseForbidden('只有作者才能编辑')
    return response
```

Django 的调用链（`django/views/generic/edit.py:144-153 / 131-134`）：

```
ProcessFormView.post → form.is_valid() → form_valid(form) → ModelFormMixin.form_valid → form.save()  ← 写库
```

`author` 不在表单 `fields` 里，所以 `form.save()` 不会改它，**判定依据本身成立——但判定发生在写入之后**。

**实际后果**：任意登录用户 `POST /written/article/<别人的pk>/edit/`，标题/正文/摘要被改写成功，响应是 403。用户看不到成功，但内容已经被改了。刷新别人的文章页就是新内容。

`get()` 里的同款检查（第 193-199 行）无害，但纯属多余——对象早已加载出来。

**修法**（把鉴权收进 `get_object()`，GET / POST 都必经）：

```python
class ArticleEditView(LoginRequiredMixin, UpdateView):
    model = Article
    form_class = ArticleEditForm
    template_name = 'written/post_written.html'

    def get_object(self, queryset=None):
        obj = super().get_object(queryset=queryset)
        if obj.author_id != self.request.user.pk:   # 提前 404，别泄露存在性
            raise Http404
        return obj
```

删掉 `get()` / `post()` 两个覆写。
难度 **S**：删 14 行、写 6 行。

### C-02 章节创建：同一 bug + 表单字段可篡改

**位置**：`written/views.py:213-230`，配合 `written/forms.py:115-117`

两个独立缺陷：

1. `post()` 同样是 `super().post()` 先写后判（写的是 `Chapter`，判的是 `Article` 的作者）。
2. **`ChapterCreationForm.Meta.fields = ('title', 'content', 'article')`**。`get_initial()` 只对 GET 生效；POST 时 `article` 直接取自 `request.POST`。攻击者把自己的文章 pk 放进 URL、把受害文章 pk 放进 `article` 字段，就能往别人文章底下挂章节——而 URL 上的鉴权（`<pk>` 是自己的）通过了。

**修法**：

```python
class ChapterCreationForm(forms.ModelForm):
    class Meta:
        model = Chapter
        fields = ('title', 'content')        # article 不再是表单字段

    def save(self, commit=True):
        self.instance.article = self.article    # 由视图从 URL 注入
        return super().save(commit=commit)


class ChapterCreateView(LoginRequiredMixin, CreateView):
    model, form_class = Chapter, ChapterCreationForm
    template_name = 'written/post_written.html'

    def get_parent_article(self):
        article = get_object_or_404(Article, pk=self.kwargs['pk'])
        if article.author_id != self.request.user.pk:
            raise Http404
        return article

    def get_form_kwargs(self):
        kwargs = super().get_form_kwargs()
        kwargs['article'] = self.get_parent_article()   # 绑定，非信任输入
        return kwargs
```

**根因提炼**：项目里有 3 处鉴权散落在 `get()`/`post()` 里（written ×2、comment 限流 ×1），全是「检查在动作外面」的同一类错误。**一次性改成「检查在对象加载处」**（`get_object()`）比逐个打补丁小。

难度 **S**（改动集中在 2 文件、约 20 行）。

### C-03 点赞只写 Redis，列表页读数据库 → 赞数永远不变

**位置**：写入 `index/redis_caches.py:69-84`，读取 `written/views.py:37`、`picture/views.py:31`

```python
# index/redis_caches.py — 写
def like(type, obj, user):
    ...
    try:
        if rd.sismember(type, oid):
            ...
            rd.sadd(oid, user.id)          # ← 只写 Redis
        else:
            rd.sadd(type, oid)
            for l in obj.likes.all():
                rd.sadd(oid, l.id)
    except (ConnectionInterrupted, RedisError):
        obj.likes.add(user)                # ← 只有 Redis 挂了才写 DB
```

```python
# written/views.py:33-39 — 读（列表页卡片）
.annotate(like_count=Count('likes', distinct=True))   # ← 读的是数据库
```

**实际后果**：

1. 用户点赞 → 只进 Redis。回到列表页，`{{ article.like_count }}` 读数据库，**数字不变**。
2. Redis 重启 / `FLUSHDB` 且没跑过 `sync_cache` → 全部点赞消失，无法恢复。
3. 详情页的 `is_likes` 读 Redis（`written/views.py:117`），列表页的 `like_count` 读数据库 —— **同一个「赞」有两套真相，同一屏里就能自相矛盾**。

浏览量 `views` 也有同样结构（`update_views` / `get_views`），但至少读写都走 Redis，症状轻一些。

**修法**：数据库是唯一事实源，Redis 只做计数缓存。这是改动最小、语义最正的方向：

```python
# 写：库为准，Redis 加速
def like(type, obj, user):
    if not obj.likes.filter(pk=user.pk).exists():
        obj.likes.add(user)          # 幂等（M2M 自身去重）
        cache.incr(f'likes:{type}:{obj.pk}')
    ...


def get_like_count(type, obj):
    key = f'likes:{type}:{obj.pk}'
    n = cache.get(key)
    if n is None:
        n = obj.likes.count()
        cache.set(key, n, 300)
    return n
```

`follow/views.py:47-52` 处理重复关注已经用了 `try/except IntegrityError` 的正确姿势，点赞照抄即可。

**顺带删掉** `sync_cache` 命令（`index/management/commands/sync_cache.py` 11 行）——没有第二个真相源就不需要同步。

**测试盲区**：`index/tests.py::test_like_then_dislike_article` 只断言按钮 id 在 `like-btn` / `dislike-btn` 之间切换，**从不检查计数或数据库状态**。C-03 因此完全漏网。

### C-04 评论提交后开放重定向

**位置**：`comment/views.py:75-76`

```python
def get_success_url(self):
    url = self.referrer = self.request.META.get('HTTP_REFERER', '/')
    ...
    return url
```

`HTTP_REFERER` 完全由客户端控制。构造请求：

```
POST /comment/create/
Referer: https://evil.com/
Content-Type: application/x-www-form-urlencoded
```

评论创建成功后 `Location: https://evil.com/`。这是标准的**开放重定向**，可与钓鱼页组合（「评论成功，请回到原页面」）。

**修法**：`Referer` 只在同站时作为兜底：

```python
from django.utils.http import url_has_allowed_host_and_scheme

def get_success_url(self):
    ...
    fallback = reverse('written:index')   # 或具体对象 URL
    ref = self.request.META.get('HTTP_REFERER', '')
    if ref and url_has_allowed_host_and_scheme(
            ref, allowed_hosts={self.request.get_host()}):
        return ref
    return fallback
```

难度 **S**（3 行 + import）。修完补一条 `Referer: https://evil.com/` 的断言。

### C-06 `@提及` 从原始 POST 重解析，目标可能 500

**位置**：`comment/views.py:78-101`

```python
def get_success_url(self):
    url = self.referrer = self.request.META.get('HTTP_REFERER', '/')
    comment = (self.request.POST.get('content') or '') + ' '   # ← 不用 self.object.content
    nicknames = re.findall(r'@(?P<nickname>[a-zA-Z0-9\u0800-\u9fa5]+) ', comment)
    ...
    target = self.model_class.objects.get(id=self.object_id)   # ← 无 DoesNotExist 保护
    author = target.author
    ...
    if author in recipients:                                  # ← queryset 的 in，整表拉取
        mentioned = True
    for recipient in recipients:
        notify.send(...)
```

四个问题：
1. **重复解析**：`get_success_url` 在 `form.save()` 之后跑，`self.object` 已经是保存好的评论，却去读原始 POST，清洗过的值被丢弃。
2. **可能 500**：`objects.get(id=...)` 无保护。`Referer` 本身就可控（C-05），目标在提交与渲染之间被删就会炸。
3. **`author in recipients`**：`recipients` 是未求值的 QuerySet，`in` 强制全量拉取到内存逐个比较。应该 `recipients.filter(pk=author.pk).exists()`。
4. **N+1 通知**：每个被 @ 的人一次 `notify.send`（逐个发，各自一条记录）。人数多时是 N 次写。

**修法**：

```python
def get_success_url(self):
    target = self.object.content_object
    author = target.author
    nicknames = set(re.findall(r'@(\w+) ', self.object.content + ' '))
    mentioned = False
    if nicknames:
        recipients = User.objects.filter(
            nickname__in=nicknames).exclude(pk=self.request.user.pk)
        mentioned = recipients.filter(pk=author.pk).exists()
        notify.send(self.request.user, recipients=list(recipients),
                    verb='@你', target=target)
    if not mentioned and author.pk != self.request.user.pk:
        notify.send(self.request.user, recipient=author,
                    verb='评论了', target=target)
    ...
```

`django-notifications-community` 的 `notify.send` 原生支持 `recipients` 为 queryset，N 次写变 1 次。
难度 **S–M**（改写约 15 行 + 加测试）。

### C-07 `get_ip()` 无条件信任 `X-Forwarded-For`

**位置**：`users/receivers.py:4-9`，被 `users/adapter.py:21`、`receivers.py:14`、`receivers.py:19` 调用

```python
def get_ip(request):
    if 'HTTP_X_FORWARDED_FOR' in request.META:
        ip = request.META['HTTP_X_FORWARDED_FOR']
    else:
        ip = request.META['REMOTE_ADDR']
    return ip
```

三个问题：
1. **可伪造**：任何客户端都能发 `X-Forwarded-For: 8.8.8.8`，直接写进 `last_login_ip` / `ip_joined`。这两个字段若被用于风控/审计，结论不可信。
2. **XFF 是逗号列表**：`1.2.3.4, 5.6.7.8`。整串塞进 `GenericIPAddressField` → `update_last_login` 的 `save()` 校验失败/截断，直接 500 或存错值。
3. **无条件信任**：即使部署在 nginx 后面，也没声明「我信任哪一跳」。

**修法**：

```python
from django.conf import settings

def get_ip(request):
    if getattr(settings, 'TRUST_X_FORWARDED_FOR', False):
        fwd = request.META.get('HTTP_X_FORWARDED_FOR', '')
        if fwd:
            return fwd.split(',')[0].strip()     # 客户端 → 代理的第一跳
    return request.META.get('REMOTE_ADDR')
```

在 `settings.py` 加一行 `TRUST_X_FORWARDED_FOR = _env_bool('DJANGO_TRUST_XFF', False)`。
难度 **S**（6 行 + settings 一行）。

### C-09 `sync_views` / `sync_like`：同步完就删源，读取却还优先读源

**位置**：`index/redis_caches.py:42-66`、`145-167`

```python
def sync_views(type):
    ...
    for k in keys:                       # k 是 bytes，如 b'1'
        o = obj.objects.get(id=k)        # IntegerField.get_prep_value 会 int()，能匹配
        cache = get_views(type, o)
        if cache != o.views:
            o.views = cache
            o.save(update_fields=['views'])
    rd.delete(type)                      # ← 删掉 Redis 里的这份
```

设计上是「Redis 攒批 → 一次性落库 → 清空 Redis」。读路径（`get_views`）仍先读 Redis，清空后走 `else` 分支重新播种，逻辑上能自洽。真正的问题：

- 只要 Redis **没重启 / 没同步**，它就一直是最新的；一旦同步后 Redis 丢了而 `sync_views` 没跑，**这期间的数据直接消失**。
- `sync_cache` 命令是**手动**的（`index/management/commands/sync_cache.py`），没有 cron / 没有 `post_save` 钩子，`deploy/` 下也没有定时任务配置。

这是 C-03 的另一面：两套真相 + 一个手动同步 = 迟早丢数据。

**修法**：同 C-03 —— DB 为唯一事实源，Redis 只做缓存，`sync_cache` 命令删除。
难度 **M**（与 C-03 合并做）。

### E-01 Redis key 用 `type[0]` 首字母 + `type+'s'`

**位置**：`index/redis_caches.py:70-71, 88-89, 113-114, 130-131`，同一段拼了 4 遍

```python
type = type + 's'
oid = type[0] + str(obj.id)     # 'articles'[0] = 'a' → 'a1'
```

`sync_like` 靠 `int(id[1:])`（第 159 行）**从 key 反解主键** —— `id[1:]` 假定首字符是类型标记。扩展性问题：
- 新增 `Audio` 类型 → `'audios'[0] == 'a'` → **和 Article 的 key 直接撞**。
- 拼串规则散在 4 个函数里，改一次要改 4 处。

`index/util.py` 已经有 `_TYPE_MAP = {'article': Article, 'picture': Picture}` 这个注册表，但只给 `what_type()` 用，redis 这边又手写了一遍。

**修法** —— 把类型元数据收进 `index/util.py` 一处，key 用无歧义分隔符：

```python
# index/util.py
_CONTENT_TYPES = {
    'article': ContentTypeDef(model=Article, key='article'),
    'picture': ContentTypeDef(model=Picture, key='picture'),
}

def what_type(type):        # 保留原签名
    d = _CONTENT_TYPES.get(type)
    return d.model if d else None

def cache_key(type, obj):   # 新增
    d = _CONTENT_TYPES.get(type)
    return f'kaku:{d.key}:{obj.pk}' if d else None
```

`type+'s'` 和 `type[0]` 全部消失，`sync_like` 直接 `int(oid.rsplit(':', 1)[-1])`。
难度 **M**（改 1 个 util + 4 个函数；缓存 key 变更需清一次缓存）。
